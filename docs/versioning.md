## 브랜치 구조

```
main              → 항상 배포 가능한 최신 안정 버전
develop            → 다음 작업을 모으는 브랜치 (또는 feature/* 에서 직접 작업)
release/x.0.0      → 특정 시점의 마일스톤 스냅샷 (frozen)
```

새 작업은 `main`에서 직접 하지 않고 `develop` 또는 `feature/*` 브랜치에서 진행한 뒤
완료되면 `main`으로 merge한다.

## release 브랜치 규칙

`release/x.0.0` 브랜치는 **"이 시점의 완성된 버전을 그대로 남겨둔다"**는 스냅샷 용도다.

- 큰 구조 개편이나 의미 있는 마일스톤을 완료했을 때 그 시점의 `main`을 그대로 분기해서 만든다
- 만든 이후에는 **원칙적으로 커밋하지 않는다** (frozen)
  - 예외: 배포된 버전에서 치명적인 버그가 발견됐을 때만 hotfix 커밋
- 브랜치명의 숫자는 `package.json`의 semver와 **1:1로 맞추지 않는다** (아래 참고)

## package.json 버전과의 관계

`release/x.0.0` 브랜치명과 `package.json`의 `version` 필드는 **서로 다른 걸 추적**한다.

| | 추적 대상 | 올라가는 시점 |
|---|---|---|
| `release/x.0.0` 브랜치명 | 마일스톤(구조 개편, 큰 리뉴얼) | 크게 갈아엎었을 때만 |
| `package.json` version | 실제 작업 단위 (커밋 단위 변경사항) | 기능/수정 쌓일 때마다 patch/minor |

즉 `release/2.0.0` 브랜치 안의 `package.json`이 `0.2.0`인 게 정상이다.
브랜치명은 "두 번째 큰 마일스톤"이라는 뜻이고, `package.json`은 그 시점까지 쌓인 실제 변경량(0.1.0 → 0.2.0)을 의미한다.

두 숫자가 안 맞는다고 버그가 아니다 — 각자 다른 걸 세고 있는 것뿐이다.

## 버전 올리는 기준

`package.json`의 `version`을 올릴 때는 일반 semver 기준을 따른다.

| 버전 | 기준 | 예시 |
|---|---|---|
| `patch` (x.x.**+1**) | 버그 수정, 기능 변화 없음 | 오타 수정, 링크 복구, 스타일 깨짐 수정 |
| `minor` (x.**+1**.0) | 기존 기능 유지 + 새 기능/콘텐츠 추가 | 새 프로젝트 섹션 추가, 신규 컴포넌트 도입 |
| `major` (**+1**.0.0) | 호환 안 되는 큰 구조 변경 → 새 `release/x.0.0` 브랜치 생성 대상 | 폴더 구조 전면 개편, 프레임워크 교체 |

새 `release/x.0.0` 브랜치를 만들지 말지는 **"이 시점을 나중에 되돌아볼 기준점으로 남겨둘 가치가 있는가"**로 판단한다.
단순 콘텐츠 수정(예: 링크 복구, 문구 수정)은 release 브랜치 없이 `main`에 바로 반영한다.
